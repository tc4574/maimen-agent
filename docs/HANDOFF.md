典型目标体验：

> “给我抽三套” → 翻卡 → “第二张，饮料换无糖” → “还是刚才那套” → “存成周五快乐餐”。

目标用户是热爱麦当劳的学生与上班族。角色、抽卡和收藏本身是用户认可的体验价值；研发应把它们与可靠的对话执行结合起来。

### 1.2 不应重新推翻的选择

- 用户已认可“角色对话 + 抽卡 + 餐品收藏”的方向，当前不需要重新开展选题脑暴。

- V1 不以摄像头为入口，优先语音、文字、点击三种输入。
- 当前优先一个“对话餐桌”与收藏入口；完整商店、论坛、门店打卡和多人对战不进入第一条实现链路。
- 先做本地运行的网页与服务，云端部署、多用户账号体系不是当前前提。

## 5. 当前核心协议：修改前必须理解

### 5.1 两个 provider

```python
ModelProvider.propose(text: str, turn: dict, state: dict) -> dict
QuoteProvider.calculate(ticket: dict) -> QuoteResult
QuoteResult(amount_cents: int, source: str, evidence_id: str)
```

两个方法都是 `async`。目前协议是 Python `Protocol`，参数和返回主体使用字典；尚无 Pydantic DTO 或跨端 JSON Schema。

`FixtureModel` 精确匹配以下三句：

| 输入 | 操作 |
| --- | --- |
| `选第二张` | `{"type":"select_card","ordinal":2}` |
| `饮料换无糖` | `{"type":"replace_item","from_sku":"demo-drink","to_sku":"demo-zero"}` |
| `撤回上一步` | `{"type":"undo"}` |

其他输入抛出 `ValueError`。UI 的演示按钮可直接产生允许的操作，不能为了支持“选第一张”就把固定脚本称为自然语言模型。

### 5.2 Harness 公开方法

| 方法 | 当前语义 |
| --- | --- |
| `create(store_id)` | 只接受两家 demo 门店；创建 demo 会话并记录首个快照 |
| `show_cards(session_id, candidates)` | 接收 1—3 个候选，为每张卡生成 ID，增加场景版本 |
| `begin_turn(session_id)` | 捕获当前卡片顺序、场景版本和新轮次 ID |
| `apply(context, operation)` | 校验 context 与允许操作后提交；一轮只能成功应用一次 |
| `interrupt(session_id)` | 清空活动轮次和 context，使相关迟到提案/报价不能生效 |
| `change_store(session_id, store_id)` | 清空卡片、草稿、撤回历史、轮次；使报价/确认失效 |
| `request_quote(session_id)` | 捕获报价 ticket，标记它为最新请求，清除此前报价和确认 |
| `accept_quote(ticket, result)` | 校验 ticket、来源、金额和时效；迟到结果记录为丢弃 |
| `confirm(session_id, quote_id)` | 为当前有效报价记录模拟确认；不属于模型允许操作 |
| `checkout_preview(session_id)` | 只返回 `demo_only_no_order_created`，支付链接为 `None` |
| `collect(session_id, name)` | 将当前草稿内容保存为本会话内的 `favorite_recipe` |

### 5.3 三种版本与几个关键字段

| 字段 | 用途 |
| --- | --- |
| `revision` | 每次持久化提交增长；SQLite 乐观写入的比较条件 |
| `scene_revision` | 卡片场景/门店变更时增长；保护卡片指代 |
| `plan_revision` | 餐单有效内容改变时增长；保护报价和确认 |
| `turn_id` / `turn_context` | 当前允许应用的模型提案与当时卡片顺序 |
| `draft` | 当前选中餐单的副本 |
| `undo` | 最多 20 个以前的草稿，不保存可复用报价 |
| `pending_quotes` | 尚未结束的报价 ticket，当前上限 8 个 |
| `latest_quote_request` | 防止同一餐单的旧请求覆盖较新的结果 |
| `quote` / `approval` | 当前报价及与其绑定的确认 |
| `collections` | 当前会话的配方列表 |

现有报价指纹包含 `session_id`、`mode`、`store_id`、`plan_revision`、`draft`。它没有真实账号作用域、就餐方式、配送费条件或券上下文；接 live 前必须扩展。

现有时效：报价结果的请求年龄须处于 0—60 秒；接受后设置 60 秒的本地有效期。两个 60 秒是应用原型规则，不是麦当劳的价格保证。

### 5.4 必须保留的不变量

1. 模型提出有限结构化操作；执行器拥有最终状态变更权。
2. 序号与输入时的卡片顺序绑定，不能按最新 UI 排序重新解释旧输入。
3. 修改会影响报价的内容后，清除对应报价和确认。
4. 撤回恢复配方内容，不复活旧报价与确认。
5. 重复提案、重复报价、过时场景、跨会话或被修改的 ticket 都不能覆盖有效状态。
6. SQLite 状态与事件写入同一事务；冲突时不能留下“已成功执行”的事件。
7. demo 与 live 来源不能混用；真实服务失败不静默使用虚构价格。
8. 收藏配方不表示真实下单、已食用或喜欢某个食物。

### 5.5 SQLite 的准确定位

目前只有 `sessions`、`events`、`schema_versions` 三张表。收藏、卡片、草稿等都嵌在 JSON 状态中，尚未独立建表。

`Store.replay()` 检查版本连续性后返回最后一个事件中的状态快照。它没有重新执行操作、验证所有中间状态或重放网络请求。对外称为“快照日志恢复”，不要写成已经实现完整事件溯源、确定性重演或不可篡改审计。

## 6. MCP 已知事实与后续接法

### 6.1 可以直接复用的部分

`connect(token)` 使用 SDK 的 `Client` 与 `streamable_http_client`，由 `httpx2.AsyncClient` 持有 Authorization。连接相关超时 15 秒、读取超时 30 秒；探针总截止时间 90 秒。

`discover()` 最多读取 10 页，并阻止重复 cursor 无限循环。工具返回的说明和 schema 是业务数据，不能作为越权执行其他工具的指令。

`call_smoke_tool()` 只允许 `now-time-info`、`list-nutrition-foods`。扩大菜单能力时新增业务适配器和明确方法，不把这里改成任意工具透传。

SDK 对象的 Python 字段如 `input_schema`、`structured_content`、`is_error`，序列化报告使用 `inputSchema`、`structuredContent`、`isError`。不要混用属性名。

### 6.2 已发现但未调用的核心工具

以下来自本机真实发现报告；不代表业务链路已经验证：

| 工具 | schema 中的必填项 | 额外业务要求 |
| --- | --- | --- |
| `query-nearby-stores` | `beType`、`searchType` | 按位置搜索时 `searchType=2`，需要 `city`、`keyword`；不能把之前去过上海总部当成当前位置 |
| `query-meals` | `storeCode`、`orderType`、`beType` | 根据取餐方式决定 `beCode`，预约条件另处理 |
| `query-meal-detail` | 上述三项 + `code` | 以真实商品编码获取套餐组成与合法修改项 |
| `query-store-coupons` | `orderType`、`beType`、`storeCode` | 券按当前用户与门店生效，不是附近人人可用的公共券 |
| `calculate-price` | `storeCode`、`orderType`、`beType` | `items` 虽未列入 schema 的 required，业务计价仍必须提供合法餐品；需补业务校验 |

初版到店自取采用 `beType=1`、`orderType=1`，说明要求不传 `beCode`。得来速、外送和团餐的业务编码规则不同，不复用到店默认值。`storeCode` 应作为字符串保留。

套餐计价结构包含 `roundList` / `comboItemList`，特制选项可能同时要求选中项的 `selectedKey` 和未选中项的 `unselectedKey`。不能把“饮料换无糖”实现为随意替换任意同类 SKU。

计价 schema 将 `price` 等金额字段标注为“分”。未来统一使用整数分，渲染时转元；完整应付金额、费用组成和券适用仍需真实调用核对。

### 6.3 营养返回不能直接用于点餐

已经成功返回的营养 `data` 是文本表格，开头为记录数量和字段头，不是 JSON 数组；当前没有解析器。内容包含产品名与营养列，但没有能直接替代门店菜单商品编码的统一键。

后续步骤：识别格式 → 解析并校验列与记录数 → 保留来源时间 → 通过门店餐品名称和规格建立明确映射。模糊匹配不足以确认规格时显示“营养未匹配”，不把猜测结果写成确定数值。

### 6.4 私密报告的使用

`artifacts/local/mcp-probe.json` 包含真实工具 schema 和两项查询结果，适合本机开发。它默认不会随源码复制/克隆出现；异机接手应重新发现工具。

当前脱敏只替换已知 Token，不是通用个人信息脱敏器。扩大到账户、地址、优惠券或订单接口后，必须按字段做脱敏和日志最小化；不能直接把整个私密报告改名后放进公开仓库。

## 7. 已知限制与优先修正项

这些项目由本次源码核对得出，本轮交接只记录，没有擅自改变业务行为。

| 优先级 | 当前限制 | 影响 | 应在哪一步解决 |
| --- | --- | --- | --- |
| 高 | Harness 直接导入 `fixtures.CATALOG`，模式和门店固定 | 无法仅替换 QuoteProvider 就接入真实数据 | 引入 Catalog/StoreContext 与受控模式工厂，保持 demo 独立 |
| 高 | 报价失败、超时或从未返回时，没有 ticket 结束清理 | 未完成请求可能累计到 8 个，之后无法再报价 | HTTP/异步服务阶段增加 failed/cancelled/expired 终态与清理 |
| 高 | 当前提案只绑定轮次和场景，未显式捕获 `plan_revision` | 新增后台改餐、跨入口同时操作时，需要更完整的版本约束 | 建立统一命令协议，提交前比较预期草稿版本 |
| 高 | `confirm()` 是可直接调用的 Python 方法 | 不能作为真实网页下单的身份和授权证明 | HTTP 会话校验、当前报价确认、下单操作记录 |
| 高 | SQLite 连接有线程约束 | 把现有 Store 放进 FastAPI 的线程池路由可能报错 | 同一执行上下文创建/使用连接，网络调用放事务外 |
| 中 | `interrupt()` 只清活动轮次，未清已接受报价/确认 | “停止播报”“取消修改”“取消购买”不能全部映射成同一个操作 | 明确 UI 语义，真实下单阶段分别实现 |
| 中 | 收藏存在会话快照，缺少跨会话查询与恢复 | 用户下一次打开应用不自动看到过去收藏 | 增加独立 favorites 与会话/本机用户归属 |
| 中 | 只有一份建表 SQL，没有升级迁移执行器 | 增加 schema 时不能只修改旧建表文件 | 新增版本迁移与旧库升级验证，保留已有数据 |
| 中 | 每个事件保存完整状态，收藏无上限，缺少删除/保留策略 | 长期使用后数据库和快照体积增长 | 收藏独立存储、会话清理、导出和保留策略 |
| 中 | 当前 API 参数是内部字典，部分非法输入可能直接抛 KeyError 等 | 不适合直接暴露成公网或浏览器协议 | Pydantic DTO、稳定业务错误码、长度/数量边界 |
| 中 | 探针屏蔽传输日志，只输出异常类型 | 后续排查失败原因不够细 | 增加经过脱敏的状态码、错误分类与关联 ID |
| 中 | 无前端事件流、重连与去重协议 | UI 可能重放旧动画或重复操作 | `command_id`、`event_id`、版本和快照同步 |
| 后续 | 没有模型评估、候选搜索或实际业务约束求解 | 不能宣称懂用户、随机抽到可买套餐或算出最优价格 | 候选引擎与模型适配阶段逐项补齐 |

同一状态的比较、乐观写入和旧报价拦截已有测试，但并未做多进程压力测试，也未证明高并发服务能力。

## 8. 后续研发工作包

下表是可执行的接手顺序。接口名称和新文件位置是建议，尚未创建。每个工作包完成后更新 README 与 MCP 状态，不把未完成层隐藏在演示数据后面。

### H01：给核心加服务边界

**目标：** 为网页提供稳定的状态、操作和事件接口，保持现有 24 项测试通过。

工作：增加 Pydantic 请求/响应类型；区分普通对话、业务操作、用户确认；建立每会话任务协调和结果提交；补报价终态清理；定义错误码与命令去重。首先只提供 demo 模式，后续通过 Catalog/StoreContext 适配 live。

建议位置：`maimen/contracts.py`、`maimen/service.py`、`maimen/api/`。复用现有 Harness/Store，不把每个 HTTP 请求都改为调用 `demo.run()`。

验收：可创建会话、读快照、选卡、替换、撤回、收藏；非法动作得到可识别的错误；旧上下文和重复命令不污染状态；超时请求可以结束并释放预算。

### H02：本地网页的文字与卡牌闭环

**依赖：** H01。**目标：** 用户能在浏览器完成 demo 流程。

创建 `web/`，采用 React + TypeScript + Vite。界面包括虚拟店员区域、最多三张餐单卡、字幕/对话区、文本输入、选卡/撤回/收藏按钮和清晰的 demo 标识。角色先用可替换的基础素材；动画由状态驱动，提供减少动画选项。

固定脚本模式明确列出支持的句子，其他输入给出真实提示；允许用按钮完成流程。卡片 ID 与服务端一致，前端不独立修改 authoritative draft 或计算最终价格。

验收：浏览器内完成“选第二张 → 换饮料 → 撤回 → 收藏”；刷新恢复同一会话；接口失败可理解；没有真实 MCP 或模型也能使用演示。交付可复现的启动命令与前端锁文件。

### H03：浏览器语音与角色状态

**依赖：** H02。**目标：** 为相同操作增加语音输入和播报，不另造状态系统。

实现按键说话、中文识别、临时字幕、最终文本提交、TTS 队列与停播。用户开始说话时先取消旧播报，再捕获当前场景。处理中不重排卡片；无法保持场景时拒绝旧指代并请求澄清。

识别能力检测、权限拒绝、网络失败、无语音、声音列表延迟加载都要处理，保留文字与点击。TTS 起止事件驱动角色说话状态，首版不做音素级口型。

验收：语音结果通过与文字相同的命令入口；中间识别结果不会执行；重复 final 事件不会重复修改；切轮次后旧语音不继续播报；真实设备人工验证并记录浏览器版本。

### H04：真实菜单、详情与计价适配

**依赖：** H01 的模式隔离和 DTO。**需要的信息：** 联调城市/门店及就餐方式；首次需要时再询问用户。

实现有类型的方法：查询门店、查询菜单、查询详情、查询门店可用券、计算价格。读取真实 schema 后补充业务规则；规范化门店、商品、套餐槽位、修改选项和报价。为 `CatalogProvider` 与 `QuoteProvider` 增加真实实现，禁止 demo ID 流入真实工具。

首先跑通一个用户选定门店的一份合法商品/套餐，再扩到多候选。营养解析是附加数据，不阻塞菜单首条链路。

验收：显示真实门店/商品/来源时间；一次修改使用实际允许的选项重新计价；缺货、券失效或接口失败会使相关报价不可继续确认；保存脱敏证据。此阶段不创建订单。

### H05：候选生成与可玩的卡牌编辑

**依赖：** H02；真实模式依赖 H04。**目标：** 抽卡从固定列表升级为有约束、有变化的候选生成。

先处理用户硬条件，再做有限候选生成、差异排序和带种子的采样；对需要展示金额的候选调用计价。实现选中卡、锁定某部分、重抽未锁定部分、撤回和配方命名。明确区分合法套餐内部替换与加购独立单品。

验收：同一组输入、工具录制结果、规则版本和随机种子可以重现候选；硬条件不会被随机过程放宽；候选不足时解释原因；不会声称未搜索全空间的全局最优。

### H06：真实模型适配

**依赖：** H01 的结构化提案；不阻塞 H02—H05。用户选择模型后才进行真实服务配置。

复用 `ModelProvider` 接口，新增明确的 `ask_clarification` / `respond` 结果，避免所有对话都强迫产生餐单修改。为预算、饮食偏好、卡片指代、替换、撤回、收藏建立 schema；限制模型调用次数和上下文大小；数据不足时澄清。

模型收到可用卡片和允许动作，不能直接看到 Token 或自由调用任意 MCP 工具。模型输出经语法、业务、版本三层校验后执行；价格等事实从工具结果填入最终回应。

验收：多种自然说法能得到正确操作；“那个”“还是之前的”不明确时询问；非法结构、未知 SKU、工具越权尝试不会修改餐单；模型失败时保留可操作 UI，而不是假装已理解。

### H07：持久收藏与第二次使用

**依赖：** H02；live 收藏依赖 H04 的标准数据结构。

增加跨会话 favorites、配方查看/命名/删除、当前门店的重新匹配与报价。保留来源和版本，把“收藏”“官方订单”“用户标记吃过”分开。首版可以只有本机用户作用域，不先建设云账号系统。

验收：关闭服务再打开仍能找到收藏；新门店重新判断可售情况；保存的旧价格不会直接成为新订单价格；删除会影响已承诺删除的本机数据。长期偏好学习另做实验，不默认存在。

### H08：故障演示与评估

**依赖：** H02；语音测试依赖 H03；真实模型评估依赖 H06。

增加工具结果录制/脱敏回放、随机种子、规则版本、调用耗时和错误分类。构造延迟、乱序、失败、重复输入、场景刷新、刷新恢复等故障场景。浏览器自动化测试文本和 UI 状态；麦克风与设备声音另做人工验证。

验收：能够复现“用户改口，旧报价迟到被拦截”的完整 UI 演示；模型评估记录分母与失败案例；性能报告区分 ASR、模型、MCP 和首个可信卡片延迟。先测再定目标，不宣称未测的低延迟或成功率。

### H09：明确确认后的真实订单

**依赖：** H04、H06 和完整的 HTTP 确认协议。属于增强阶段，不能阻塞只读体验的试用。

增加 `order_attempts`、当前报价确认面板、用户操作凭据、单次本地提交和未知结果恢复。调用前持久化尝试，超时后进入 `unknown_outcome`；通过官方查询核实，无法唯一确认时请用户核对，不能自动重复创建。

验收：旧确认不能用于改过的餐单；双击或重放请求不额外发起创建；网络不确定状态不显示虚假的失败/成功；支付入口来自官方结果。开发采用模拟服务测试，真实创建需要具体餐单的用户确认。

### H10：发布、试用与参赛交付

## 10. 建议的 API 与事件约定（尚未实现）

### 10.1 服务接口草案

| 接口 | 用途 |
| --- | --- |
| `POST /api/sessions` | 创建明确模式的会话 |
| `GET /api/sessions/{id}` | 返回用于 UI 的快照，不包含凭据或内部敏感数据 |
| `POST /api/sessions/{id}/turns` | 开始输入轮次，验证客户端所见场景版本并捕获卡片顺序 |
| `POST /api/sessions/{id}/commands` | 提交最终文本或点击动作，携带命令 ID、轮次及预期版本 |
| `POST /api/sessions/{id}/interrupt` | 终止当前生成/播报任务；返回新的活动轮次状态 |
| `GET /api/sessions/{id}/events`（WebSocket 升级） | 推送带序号的业务事件，支持重连恢复 |
| `POST /api/sessions/{id}/confirmations` | 未来独立用户确认入口，不作为模型动作暴露 |

最终可调整路径，但命令去重、版本检查、会话归属、错误语义必须保留。首版仅绑定 `127.0.0.1`，配置允许的开发前端来源和本机会话凭据；不要默认开放任意跨域访问。

### 10.2 推荐事件字段

```json
{
  "event_id": "server-generated-id",
  "sequence": 12,
  "session_id": "session-id",
  "turn_id": "turn-id-or-null",
  "revision": 12,
  "scene_revision": 3,
  "plan_revision": 5,
  "type": "quote_ready",
  "source": "demo",
  "payload": {}
}
```

字段是协议草案，不是现有接口响应。事件以服务端为准，前端忽略重复序号和已经过时的轮次，断线后先同步快照再恢复增量。动画和播报消费同一版本结果，不能在重连后重复执行购买或重新播放全部历史动画。

适合的事件包括 `turn_started`、`scene_presented`、`draft_changed`、`quote_pending`、`quote_ready`、`quote_discarded`、`clarification_required`、`recipe_collected`、`operation_failed`。对用户显示简洁状态，开发调试信息放在独立面板。

### 10.3 Agent 提案草案

建议用判别联合区分 `operation`、`clarification`、`response`，每个提案包含来源轮次、预期场景/餐单版本和有限 payload。工具调用计划只能引用当前后端暴露的能力，不接受任意 URL、Python 代码或工具名称透传。

一个用户句子含多个修改时，先明确采用“原子批次”还是“逐步操作并可恢复”。当前 Harness 一轮只允许一次操作，不能直接循环调用 `apply()` 伪装多步事务。
